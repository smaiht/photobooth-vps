# Photobooth VPS

VPS связывает Telegram с фотобудкой через сервисы Яндекса:

- media: файлы в `<event>`, уведомления `session_ready` в
  `photobooth_system/control/to_vps`;
- commands: `photobooth_system/control/to_booth`;
- command responses: общий с сессиями `photobooth_system/control/to_vps`;
- обработанные служебные JSON удаляются, логи лежат в
  `photobooth_system/control/logs`;
- update artifacts and `status.json`: `photobooth_system/updates` на Диске;
- delivery: Telegram Bot API.

## Event workflow

1. Отправить `/event Название события` Telegram-боту.
2. Дождаться подтверждения будки и VPS.
3. После тестовой сессии убедиться, что медиа появились в event-корне, а
   `session_*.json` был удалён из `control/to_vps` после доставки в Telegram.
4. Отправить `/link` и передать владельцу полученный `public_url`.

VPS раз в 10 секунд листит один стабильный `to_vps`. Ответы команд и готовые
сессии обрабатываются независимыми asyncio workers, поэтому загрузка видео не
блокирует подтверждение команды. VPS не удаляет и не перемещает медиа. При
ошибке скачивания или Telegram сообщение остаётся в `to_vps` и повторяется.
`session_ready` содержит свой `event_folder`, поэтому доставка не зависит от
одновременного переключения event на будке и VPS. `/event` отклоняется будкой,
если ещё идёт сессия или локальная загрузка.

Это protocol v2 с новыми путями. При переходе нужно дождаться пустых старых
`_sessions/inbox`, `commands/inbox` и `responses`, затем обновить будку первой,
а VPS сразу после неё. Старые каталоги после перехода не поллятся.

## Настройки камеры через Telegram

Команда `/get_config` возвращает администратору два отдельных документа одним
Telegram media group. `photobooth_configs.txt` приходит с будки через
Яндекс.Диск и содержит сначала актуальный `config_app.json`, затем
`config_camera.json`. `config_vps.json` читается и отправляется напрямую с VPS;
секреты из `.env` в него не входят. После успешной отправки временная копия
файла будки удаляется с Диска. Команда ничего не меняет и не перезапускает
будку.

Администратор может изменить любое существующее рабочее поле
`config_camera.json` командой `/<поле> <значение>`, например `/iso 200`,
`/iso auto`, `/white_balance auto`, `/av 6.3` или `/continuous_af false`.
VPS передаёт имя поля и исходное значение без собственной копии схемы; тип,
допустимые `_..._options` и наличие поля проверяет будка по актуальному конфигу.

При успешной проверке будка атомарно записывает изменившийся конфиг, публикует
ответ для Telegram в надёжный канал Диска и затем штатно перезапускается. Уже
установленное значение не перезаписывает файл, но рестарт всё равно выполняется:
это гарантирует применение настройки и делает повтор команды после временного
сбоя доставки безопасным.
Неизвестные и служебные `_...` поля, неверные значения и команды во время
активной фотосессии отклоняются без изменения файла и без рестарта.

## Печать изображения из Telegram (MVP)

Пользователи с Telegram ID `6634566969` и `5683598562` могут прислать боту
одно изображение как обычное Telegram-фото либо как image-документ размером до
20 МБ. VPS сохраняет исходные байты без перекодирования. Будка определяет формат
по содержимому через Pillow; кроме стандартных JPEG, PNG, WebP, BMP, TIFF и GIF
подключён декодер HEIC/HEIF/AVIF. Медиальбом целиком отклоняется: каждое фото
нужно отправлять отдельным сообщением.

VPS знает активный event и сохраняет два обычных отдельных файла прямо в
`<event>_by_sessions/0000_print_jobs`. Префикс `0000_` ставит служебную папку
первой при сортировке по имени в Яндекс.Диске. Имя файла содержит Telegram
user ID, UTC-время и уникальный job ID; рядом лежит одноимённый `.txt` с данными пользователя,
сообщения, исходного файла и задания. Команда в `control/to_booth` содержит
ссылку на этот оригинал, отдельной временной копии на Диске нет.

Будка скачивает сохранённый оригинал и целиком вписывает его без обрезки в лист
4×6. Если `width > height`, сразу создаётся горизонтальный лист `3688×2480`.
Если `width <= height`, исходник сначала поворачивается на 90° против часовой
стрелки. Затем он целиком вписывается в горизонтальный белый лист `3688×2480`.
Таким образом, в существующую очередь и непосредственно драйверу принтера во
всех случаях передаётся горизонтальное изображение `3688×2480`, а на бумаге
фотография правильно выглядит при соответствующем горизонтальном или
вертикальном положении листа. Исходник любого разрешения масштабируется до
максимального размера внутри листа; белые поля возникают только при отличии его
пропорций от 3:2. Квадрат считается вертикальным и получает одинаковые белые
поля сверху и снизу. Маленький исходник будет увеличен и может выглядеть менее
резким, но не останется маленьким посередине листа. Локальный подготовленный
файл удаляется после печати, а два исходных файла на Яндекс.Диске остаются.
Отправитель получает
подтверждение через обычный control-response.

## Обновления

CI только собирает `photobooth-win.zip` и GitHub Release. Токен Диска в GitHub
Secrets не нужен.

```text
push в main → дождаться успешного GitHub Actions
             → /update
             → VPS перезаписывает artifacts/full.zip на Диске
             → status.json записывается последним
             → администратор отправляет /restart
```

`status.json` хранит метаданные единственного полного артефакта и совместимое
поле `active: "full"`. Будка сравнивает SHA ZIP с локальным `.update_hash`;
отдельной нумерации версий нет. `/update` использует готовый Windows release,
будке доступ к GitHub не нужен.

VPS скачивает release для проверки ZIP, а на Диск файл попадает через
server-side import конечного GitHub asset URL. После проверки size/MD5 временный
ресурс атомарно заменяет `artifacts/full.zip`, и только затем публикуется
`status.json`. Если URL-import временно падает, VPS делает до пяти попыток с
экспоненциальными паузами 2, 4, 8 и 16 секунд. Каждый сбой, следующая пауза и
успешное восстановление сообщаются администратору в Telegram. Только после пяти
неудач включается медленный прямой PUT с прогрессом и 30-минутным timeout; о
переходе на fallback бот сообщает отдельно.

## Переменные окружения

- `YADISK_TOKEN` — один действующий OAuth-токен Диска на VPS и будке;
- `TG_BOT_TOKEN`, `TG_CHAT_ID`, `TG_ADMIN_ID` — Telegram;
- `GITHUB_RELEASE_URL` — URL `photobooth-win.zip` из release `latest`.
- `POSTGRES_PASSWORD` — обязательный пароль локального PostgreSQL;
- `POSTGRES_DB`, `POSTGRES_USER` — необязательные имя базы и пользователь,
  по умолчанию оба используют `photobooth`.
- `DB_HOST=postgres`, `DB_PORT=5432` — адрес PostgreSQL внутри Compose-сети;
  `DB_NAME`, `DB_USER`, `DB_PASSWORD` можно задать отдельно, иначе приложение
  использует соответствующие `POSTGRES_*`.

`docker-compose.yml` загружает их из локального `.env`. Секреты не хранятся в
репозитории.

## PostgreSQL и миграции

Compose запускает PostgreSQL 18 в сервисе `postgres`; данные лежат в именованном
volume `postgres_data` и переживают пересоздание контейнеров. Порт базы наружу
не публикуется.

После успешного healthcheck PostgreSQL сервис `app` запускается и первым делом,
до Telegram и Яндекс.Диска, применяет новые SQL-файлы из `migrations/`.
Применённые версии, SHA-256 исходного SQL и время хранятся в
`schema_migrations`. Advisory lock защищает от одновременного запуска двух
экземпляров. Уже применённый файл менять нельзя: проверка checksum остановит
запуск; изменение схемы добавляется следующим файлом, например
`0002_events.sql`.

Первая миграция создаёт:

- `bot_users` — общую таблицу пользователей Telegram и MAX с уникальной парой
  `(provider, provider_user_id)`, первым и текущим параметрами `/start`;
- `bot_start_events` — отдельную неизменяемую историю запусков без JSON-массива.

Telegram `/start` уже записывается в эти таблицы. Повторная доставка одного
`update_id` не создаёт повторное событие. Поле `language_code` не хранится.
Схема готова для `provider=max`; когда появится MAX-обработчик, он будет вызывать
тот же слой `database.record_bot_start`.
