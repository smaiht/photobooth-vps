# Photobooth VPS

VPS связывает Telegram с фотобудкой через сервисы Яндекса:

- media: файлы в `<event>`, уведомления `session_ready` в
  `photobooth_system/control/to_vps`;
- commands: `photobooth_system/control/to_booth`;
- command responses: общий с сессиями `photobooth_system/control/to_vps`;
- обработанные служебные JSON удаляются, логи лежат в
  `photobooth_system/control/logs`;
- update artifacts and `status.json`: `photobooth_system/updates` на Диске;
- delivery: Telegram Bot API.

## Event workflow

1. Отправить Telegram-боту `/event 2026-08-17 Свадьба Ивановых`. Название
   должно начинаться с настоящей даты `YYYY-MM-DD`; единственное исключение —
   технический event `/event Кафе`.
2. Дождаться подтверждения будки и VPS. Бот сразу опубликует папку event и
   вернёт её `public_url`. Для обычного мероприятия он также вернёт короткий
   `start`-параметр вида `ev_...` для QR-ссылки
   `https://t.me/<bot>?start=<параметр>`.
3. После тестовой сессии убедиться, что медиа появились в event-корне, а
   `session_*.json` был удалён из `control/to_vps` после доставки в Telegram.

Технический event `Кафе` блокирует запуск съёмки на idle-экране будки.
Администратор открывает точное число следующих сессий командой `/unblock N`;
`/unblock` без числа означает одну сессию. Счётчик уменьшается только после
успешно завершённой фотосессии и сохраняется на будке между рестартами и
обновлениями. Обычные event этой блокировкой не ограничиваются.

`start`-параметр детерминированно считается как HMAC-SHA256 от нормализованного
названия event с секретом `EVENT_KEY`. Секрет находится только на VPS; будке он
не нужен. Получив непустой `/start`, бот сохраняет его как текущий параметр
пользователя. Обычный `/start` без параметра ранее сохранённый доступ не
стирает. Отдельной таблицы мероприятий и `event_id` в MVP нет: при выборе
печати VPS сравнивает сохранённый параметр пользователя с токеном текущего
event.

VPS раз в 10 секунд листит один стабильный `to_vps`. Ответы команд и готовые
сессии обрабатываются независимыми asyncio workers, поэтому загрузка видео не
блокирует подтверждение команды. VPS не удаляет и не перемещает медиа. При
ошибке скачивания или Telegram сообщение остаётся в `to_vps` и повторяется.
`session_ready` содержит свой `event_folder`, поэтому доставка не зависит от
одновременного переключения event на будке и VPS. `/event` отклоняется будкой,
если ещё идёт сессия или локальная загрузка.

Это protocol v2 с новыми путями. При переходе нужно дождаться пустых старых
`_sessions/inbox`, `commands/inbox` и `responses`, затем обновить будку первой,
а VPS сразу после неё. Старые каталоги после перехода не поллятся.

## Настройки камеры через Telegram

Команда `/get_config` возвращает администратору два отдельных документа одним
Telegram media group. `photobooth_configs.txt` приходит с будки через
Яндекс.Диск и содержит сначала актуальный `config_app.json`, затем
`config_camera.json`. `config_vps.json` читается и отправляется напрямую с VPS;
секреты из `.env` в него не входят. После успешной отправки временная копия
файла будки удаляется с Диска. Команда ничего не меняет и не перезапускает
будку.

Администратор может изменить любое существующее рабочее поле
`config_camera.json` командой `/<поле> <значение>`, например `/iso 200`,
`/iso auto`, `/white_balance auto`, `/av 6.3` или `/continuous_af false`.
VPS передаёт имя поля и исходное значение без собственной копии схемы; тип,
допустимые `_..._options` и наличие поля проверяет будка по актуальному конфигу.

При успешной проверке будка атомарно записывает изменившийся конфиг, публикует
ответ для Telegram в надёжный канал Диска и затем штатно перезапускается. Уже
установленное значение не перезаписывает файл, но рестарт всё равно выполняется:
это гарантирует применение настройки и делает повтор команды после временного
сбоя доставки безопасным.
Неизвестные и служебные `_...` поля, неверные значения и команды во время
активной фотосессии отклоняются без изменения файла и без рестарта.

## Печать изображения из Telegram (MVP)

Бот сразу отвечает на полученное изображение, что начал обработку. В обычном
event продолжить могут allowlist-пользователи и гости, которые открыли бота по
QR именно текущего мероприятия. Доступ гостя проверяется до скачивания фото и
действует, пока активно это название event. После успешной постановки задания
гостя в очередь следующая печать доступна через пять минут. В один момент у
пользователя может быть только одно незавершённое задание.

В техническом event `Кафе` прислать изображение может любой пользователь.
После выбора формата бот сразу подтверждает выбор пользователю, убирает кнопки,
а затем отправляет администратору фото, сведения о пользователе и кнопки
`Разрешить` / `Отклонить`. Разрешение означает, что наличная оплата принята:
пользователь сразу получает одно сообщение о постановке фото в очередь, после
чего задание передаётся будке. Повторное нажатие кнопки не создаёт вторую
печать. Allowlist-пользователи, включая `TG_ADMIN_ID`, проходят сразу без
подтверждения и без гостевого кулдауна.

VPS определяет формат по содержимому, учитывает EXIF-поворот и принимает его
через Pillow; кроме стандартных JPEG, PNG, WebP, BMP, TIFF и GIF подключён
декодер HEIC/HEIF/AVIF. Медиальбом целиком отклоняется: каждое фото нужно
отправлять отдельным сообщением.

Горизонтальная цель имеет пропорции `3688×2480`, вертикальная и квадратная —
`2480×3688`. Если пропорции исходника совпадают точно (само разрешение может
быть любым), режим `fit` выбирается автоматически, потому что ни полей, ни
обрезки не будет. В `Кафе` такое задание всё равно сначала ожидает решения
администратора. При любом несовпадении бот отвечает на исходное сообщение одним
коллажем и кнопками:

- `1️⃣ Как есть` (`fit`) — всё фото по центру, свободное место листа белое;
- `2️⃣ Увеличить` (`fill`) — фото заполняет лист, центральная область останется,
  а затемнённые красным части будут обрезаны;
- `❌ Отмена` — удаляет локальное ожидающее задание без отправки на печать.

Если обрезка идёт сверху и снизу, два варианта стоят рядом. Если слева и справа,
они стоят друг под другом, поэтому затемнённые края не мешают сравнению. До
выбора исходник находится только локально в `print_pending_jobs/<job_id>` и на
Яндекс.Диск не загружается. Выбрать вариант или отменить задание может только
отправитель, срока у кнопок нет. После успешной передачи задания локальная
pending-копия удаляется; повторное нажатие не создаёт вторую печать. Для
пересланного изображения отправителем считается переславший его пользователь:
бот отвечает в текущий чат и не обращается к автору оригинала.

После выбора и требуемой авторизации VPS сохраняет два обычных отдельных файла
прямо в `<event>_by_sessions/0000_print_jobs`. Event фиксируется при получении фото,
поэтому его последующая смена не переместит ожидающее задание в другое событие.
Префикс `0000_` ставит служебную папку первой при сортировке по имени в
Яндекс.Диске. Имя файла содержит Telegram user ID, UTC-время и уникальный job ID;
рядом лежит одноимённый `.txt` с данными пользователя, сообщения, исходного
файла и выбранного режима. Команда в `control/to_booth` содержит ссылку на этот
оригинал, отдельной временной копии на Диске нет.

Будка скачивает сохранённый оригинал и применяет выбранный `fit` или `fill`.
Перед скачиванием она обязательно сравнивает `event_folder` задания со своим
активным event. Поэтому команда от предыдущего мероприятия не попадёт в новую
очередь после переключения будки.
Если `width > height`, сразу создаётся горизонтальный лист `3688×2480`. Если
`width <= height`, исходник сначала поворачивается на 90° против часовой
стрелки, после чего применяется тот же режим.
Таким образом, в существующую очередь и непосредственно драйверу принтера во
всех случаях передаётся горизонтальное изображение `3688×2480`, а на бумаге
фотография правильно выглядит при соответствующем горизонтальном или
вертикальном положении листа. Маленький исходник масштабируется до листа и
может выглядеть менее резким, но не останется маленьким посередине. Локальное
хранение оригинала и подготовленного JPEG на будке управляется её параметром
`keep_custom_print_files`; два файла на Яндекс.Диске остаются. Отправитель
получает подтверждение постановки в очередь через обычный control-response.

## Обновления

CI собирает `photobooth-win.zip`, обновляет GitHub Release `latest`, автоматически
публикует ZIP в Яндекс.Диск и сообщает результат администратору в Telegram.
Workflow использует GitHub Secrets `YADISK_TOKEN`, `TG_BOT_TOKEN` и
`TG_ADMIN_ID`.

```text
push в main → GitHub Actions перезаписывает artifacts/full.zip на Диске
             → status.json записывается последним
             → администратор получает Telegram-уведомление
             → администратор отправляет /restart
```

`status.json` хранит метаданные единственного полного артефакта и совместимое
поле `active: "full"`. Будка сравнивает SHA ZIP с локальным `.update_hash`;
отдельной нумерации версий нет. `/update` остаётся ручным резервным способом
повторной публикации готового Windows release; будке доступ к GitHub не нужен.

GitHub Actions и ручной `/update` используют одинаковый порядок: проверяют ZIP,
до пяти раз пробуют server-side import конечного GitHub asset URL, сверяют
size/MD5, атомарно заменяют `artifacts/full.zip` и только затем публикуют
`status.json`. После пяти неудач CI напрямую загружает локальный ZIP со своего
временного runner-а, а VPS — скачанную локальную копию со своего процесса.

## Переменные окружения

- `YADISK_TOKEN` — один действующий OAuth-токен Диска на VPS и будке;
- `TG_BOT_TOKEN`, `TG_CHAT_ID`, `TG_ADMIN_ID` — Telegram;
- `EVENT_KEY` — секрет HMAC для event QR; задаётся только на VPS и не передаётся
  фотобудке;
- `GITHUB_RELEASE_URL` — URL `photobooth-win.zip` из release `latest`.
- `POSTGRES_PASSWORD` — обязательный пароль локального PostgreSQL;
- `POSTGRES_DB`, `POSTGRES_USER` — необязательные имя базы и пользователь,
  по умолчанию оба используют `photobooth`.
- `DB_HOST=postgres`, `DB_PORT=5432` — адрес PostgreSQL внутри Compose-сети;
  `DB_NAME`, `DB_USER`, `DB_PASSWORD` можно задать отдельно, иначе приложение
  использует соответствующие `POSTGRES_*`.

`docker-compose.yml` загружает их из локального `.env`. Секреты не хранятся в
репозитории.

## PostgreSQL и миграции

Compose запускает PostgreSQL 18 в сервисе `postgres`; данные лежат в именованном
volume `postgres_data` и переживают пересоздание контейнеров. Порт базы наружу
не публикуется.

После успешного healthcheck PostgreSQL сервис `app` запускается и первым делом,
до Telegram и Яндекс.Диска, применяет новые SQL-файлы из `migrations/`.
Применённые версии, SHA-256 исходного SQL и время хранятся в
`schema_migrations`. Advisory lock защищает от одновременного запуска двух
экземпляров. Уже применённый файл менять нельзя: проверка checksum остановит
запуск; изменение схемы добавляется следующим файлом, например
`0003_next_change.sql`.

Первая миграция создаёт:

- `bot_users` — общую таблицу пользователей Telegram и MAX с уникальной парой
  `(provider, provider_user_id)`, первым и текущим параметрами `/start`;
- `bot_start_events` — отдельную неизменяемую историю запусков без JSON-массива.

Telegram `/start` уже записывается в эти таблицы. Повторная доставка одного
`update_id` не создаёт повторное событие. Поле `language_code` не хранится.
Схема готова для `provider=max`; когда появится MAX-обработчик, он будет вызывать
тот же слой `database.record_bot_start`.

Вторая миграция создаёт `print_jobs`. В ней фиксируются пользователь, текущее
имя event, выбранный `fit`/`fill`, вид авторизации, `command_id` и переходы от
обработки фотографии до ответа будки. Частичный уникальный индекс не даёт двум
незавершённым заданиям одного пользователя одновременно пройти через разные
процессы VPS. Та же запись атомарно защищает подтверждение кассира и повторные
нажатия Telegram-кнопок. Изображения в PostgreSQL не хранятся.
